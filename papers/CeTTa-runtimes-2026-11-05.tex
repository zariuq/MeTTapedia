\section{Application Measurements: 5 November 2026}
\label{app:runtimes-20261105}

This appendix measures the November preview against the reference
implementation of each comparison: standalone MORK on its own MM2 programs,
SWI-\PeTTa{} on the \PeTTa{} examples and on a learning program, Hyperon
Experimental on shared \HE{} programs, and the Python ai-mathematician on its
premise-selection stage.  Every timed run was checked: a run counts only if its
answers agree with an independent oracle or with the reference's complete
result set, as stated with each table, and a run that did not finish is
reported as such, never as a time.  Measurements from earlier dates are kept
only in Section~\ref{app:runtimes-earlier}, separate from these.

\subsection{Systems and method}
\label{app:runtimes-method}

\begin{description}
\item[\CeTTa{}.] Version 1.5.0-dev, the default build (Python support, no
  MORK bridge), built from pre-main commit \code{2ca1c923} with the preview
  repairs then staged; executable SHA-256 prefix \code{18091c10633b}.  The
  \PeTTa{} lane is \code{-{}-lang petta}.  The Opt suite and the MORK
  side-by-side programs also select \code{-{}-profile extended}, whose
  \code{(new-space set)} gives the set semantics MM2's spaces have.
\item[MORK.] Commit \code{1c44f70} (the current upstream \code{main}) with
  \PathMap{} \code{fb979b4}, release builds with nightly Rust.  The
  \emph{default} build joins relation by relation through MORK's product
  zipper (prefix \code{88c740354eae}); the \emph{leapfrog} build enables
  MORK's experimental variable-at-a-time leapfrog join for flat conjunctive
  bodies (prefix \code{0e5082db27cb}).  Each run is
  \code{mork run IN.mm2 OUT.mm2 -{}-instrumentation 0}.
\item[SWI-\PeTTa{}.] \PeTTa{} commit \code{b74af1b} with local, uncommitted
  fixes (typed calls use only declarations of their own arity, an empty
  \code{superpose} fails, reader and launcher changes), on SWI-Prolog 10.1.9,
  run as \code{run.sh FILE -{}-silent}.
\item[Hyperon Experimental.] \code{metta-repl} 0.2.10 built from the fork
  branch \code{fixes} (\code{b1b2206a}): upstream release 0.2.10 plus three
  fixes (imports, space index and numbers; argument type errors; evaluated
  flags after nested substitutions).  Prefix \code{32b45f7dbeec}.
\item[Machine.] A shared workstation with an AMD Ryzen 7 9800X3D (eight
  cores, sixteen logical CPUs) and 59\,GiB of memory, Linux 7.0.  Other
  agents' jobs kept its one-minute load average between about 5 and 21 at the
  starts of the measurement batches, and above 20 at times.  Each batch waited briefly for a quieter moment and then
  ran every job pinned to the logical CPU that was least busy at its start; the
  start load of every batch is recorded with the data.  Repeated trials varied
  little (MORK's backward chainer, for instance, took 14.4--14.8\,s), but the
  absolute times are those of a shared machine.  Jobs ran with
  \code{RAYON\_NUM\_THREADS=1} and an unlimited stack for every engine (MORK
  recurses over term depth; with the default stack its unary-clock programs
  abort).
\end{description}

\noindent Every cell is the median of three fresh processes, run in
alternating engine order; times are in seconds unless a column says
otherwise.  \emph{Wall} is the whole process: start-up,
loading, execution and output.  \emph{CPU} is user plus system time.
\emph{MiB} is the peak resident set.  Some batches also counted user-mode
instructions, whose counter adds about 7\,ms to each wall time.  In the
application table, \CeTTa{}'s and the leapfrog build's times come from runs
without the counter; the default build's and SWI-\PeTTa{}'s include it, which
matters only for their cells below 0.3\,s.  The scale ladder counted
throughout.  MORK's
\emph{execute} column is the
execution time MORK itself reports; it excludes reading its input and writing
its final store, which it serializes completely, while the MeTTa programs print
only their relation sizes.  The MORK columns therefore bracket its time: the
execute column alone is the comparison least favourable to \CeTTa{}, whose
cells always include loading and output.  Ratios in the text compare
\CeTTa{}'s wall time with MORK's execute time.

\subsection{The Opt application suite}
\label{app:runtimes-opt}

The suite pairs nine tasks written as MM2 programs with ordinary \PeTTa{}
programs over the same generated facts.  The MM2 programs are MORK's: the
two-hop and triangle join, the five-clique query, the process calculus, the
odd--even sort and the backward chainer \code{bc3} come from MORK's kernel
benchmarks (several at MORK's own benchmark sizes), the counter machine from
its resources, and Hexlife and the path-producing reachability from its
tutorials.  The \PeTTa{} programs are idiomatic solutions of the same tasks,
not translations of the MM2 rules, and three of them use a different
algorithm: the counter machine runs as a function over the machine state that
records every state, where MM2 fires one clocked rule per step; backward proof
search is a depth-bounded top-down search per target, where MM2's \code{bc3}
saturates goals and evidence on a clock; and Hexlife counts each candidate
cell's live neighbours directly, where MM2 uses count sinks.  The comparison is
between two systems' solutions of one task, checked to compute one result
relation.  The graph workload computes the distinct two-hop endpoint pairs and
the directed closed triples of a random graph; it is not a fixed-point
transitive closure.

\paragraph{Checks.}  Before any timing, every pair was run with complete output:
the full set of every result relation, alpha-normalized, with the process
calculus's \code{!}, \code{?} and \code{|} renamed to its \PeTTa{} constructors,
was compared with MORK's final store.  The comparison was made at the small
control sizes and again at the timed sizes, where the largest set has
1,080,571 rows; all 27 runs at each size agreed for \CeTTa{}, SWI-\PeTTa{} and
the default MORK build, and the leapfrog build agreed too.  Every timed run
then checks every relation's size against MORK.  Independent Python
computations confirm the graph counts (bit sets or hash sets: 1,064,228 pairs
and 16,343 triangles at 49,727 edges; 4,794,018 and 16,961 at 200{,}000 draws;
19,913,332 and 8,935 at one million; 99,909,346 and 8,356 at five million), the
five-clique counts (79 and 637) and the counter machine's state rows (an
integer machine: 16,218 at register value 300, 54,018 at 1,000).

\paragraph{A corrected program.}  The complete-set check exposed an error in
the original \PeTTa{} counter program: it stored
\code{(add-atom \&m (state \$pt (IC (peano \$ic))))}, and an atom being
added is data, so the instruction counter held the unevaluated
\code{(peano \$ic)}.  SWI-\PeTTa{} and \CeTTa{} agree on that reading.  Row
counts matched MORK's, but at register value 3, 30 instruction-counter rows
differed.  The corrected program binds the computed numeral first.  Earlier
counter timings measured the faulty program and are withdrawn.

\paragraph{Reading the table.}  \CeTTa{}'s whole process is faster than MORK's execution alone in every row,
against both builds.  Against the faster of MORK's two builds for each task the
factor is 2.4 for the odd--even sort and 2.5 for ancestry; 5--7 for the
five-cliques, the two-hop pairs and the counter machine; 18 for the process
calculus; and 200--460 for backward proof search, reachability and Hexlife.
For those three and for the counter machine the two programs use different
algorithms, so their factors compare solutions rather than engines.  MORK's
two builds differ by up to 580 times (the five-cliques in the benchmark's order)
and 13 times (the counter machine); the leapfrog join is slower than the default
one only on reachability (7.55 against 6.93\,s) and ties on the sort, so a
comparison with one build alone would misstate MORK.  \CeTTa{} uses more memory than MORK on most of these
small inputs, where its start-up footprint of about 13\,MiB dominates, and less
on the two-hop pairs, reachability and the counter machine.  SWI-\PeTTa{} is
faster than both MORK builds on the four tasks whose \PeTTa{} programs search
differently, slower than MORK's faster build on the other five, and needs up to
1.1\,GiB where \CeTTa{} needs under 50\,MiB.  User-mode instruction counts,
taken in a separate batch of the same programs, are independent of the
machine's load and tell the same story: 0.04 billion for \CeTTa{}'s whole
five-clique process against 419 billion for MORK's default build in the
benchmark order and 2.1 billion in the early order, and 1.9 against 17 billion
for the two-hop pairs.  On the counter machine SWI-\PeTTa{} executes fewer
instructions than \CeTTa{} (20 against 27 billion) and still takes longer.

\paragraph{Order of a conjunction.}  MORK's default join follows the written
order of an \code{exec} body.  The five-clique row uses MORK's own benchmark
query, which lists the ten edge conditions lexicographically.  Written so that
each new vertex's edges are checked as soon as it is introduced, the same MM2
query is the row marked ``early order''; the \PeTTa{} program is unchanged,
since \CeTTa{} chooses its own join order.  With that order MORK's default build executes the query in 0.094\,s instead
of 18.7\,s; the leapfrog build takes 0.032\,s in either order, and \CeTTa{}
0.006\,s.

to 15\% fewer instructions), and the two base cases run back to back, proof
search and ancestry, are level.  These are
regressions of the preview to be repaired, not properties of the programs.

\subsection{MORK's showcase workloads with its leapfrog join}
\label{app:runtimes-leapfrog}

A second suite was written to meet MORK on ground it was built for: graph
analytics, knowledge-graph queries and combinatorial search, at sizes from
thousands to millions of facts, each with an MM2 program for MORK, a
\PeTTa{} program for \CeTTa{} and an independent Python oracle in its
generator.  LDBC Graphalytics kernels run on Graph500 Kronecker graphs
(breadth-first depths, weakly connected components, deterministic label
propagation, local clustering coefficients and single-source shortest paths at
scales 12 and 14; the first three at scale 16); LUBM queries run on 1, 5 and 10
generated universities; four LDBC SNB business-intelligence queries run on
LDBC's own SF0.1 and SF0.3 data, returning their full results without the
queries' final top-$k$ limit.  The rest are Hilbert-style proof search by
backward chaining done as forward chaining (MORK's own \code{bfc} benchmark),
simulation signatures of a 4,096-bit adder for equivalence checking,
condensed-detachment saturation in three axiom systems, CTL model checking of
the dining philosophers, approximate matching of sequencing $k$-mers by masked
views, five-cliques on 800 vertices with MORK's best conjunction order, Apriori
frequent itemsets, and analytics over a million-fact knowledge graph shaped like
MORK's FlyBase workload.  The reference is MORK's leapfrog build.  A run
passes only if every relation's size equals the oracle's and, for the 34 tasks
whose oracle lists rows, the complete row set equals the oracle's.  The
generators are in \code{benchmarks/mork\_leapfrog/}; the SNB inputs need the
official LDBC datasets.

\subsection{The \HE{} lane against Hyperon Experimental}
\label{app:runtimes-he}

The same source file and the same independent expected answer bag for both
engines; \CeTTa{} runs \code{-{}-lang he}.  Twenty-three cases were attempted
with a 600-second limit per run.  Seventeen completed on both engines with the expected answers and are
timed below.  Hyperon Experimental aborted on three of the larger joins
(\nolinkurl{triangle_dense_32_count}, \nolinkurl{guarded_triangle_32_count},
\nolinkurl{path_product_12_cardinality_count}) at an assertion of its
expression index (\code{size < TK\_MAX\_EXPRESSION\_SIZE}); \CeTTa{}
answered all three correctly.  Three path cases
(\nolinkurl{path_product_12_count}, \nolinkurl{path_product_12_separator_count},
\nolinkurl{path_isolated_8_512_count}) use \CeTTa{}'s extended \code{fold},
which Hyperon Experimental, following MeTTa's rule for unknown symbols, leaves
uninterpreted; they are not portable programs and are not compared.  No run
reached the limit.

\subsection{The ai-mathematician}
\label{app:runtimes-aimath}

The ai-mathematician, a theorem-proving pipeline over a Megalodon corpus,
has a \PeTTa{} port that runs on \CeTTa{}; its original is in Python.  The
stage that runs without external provers is premise selection: for each of the
966 theorems of the 1,158-declaration corpus that have recorded dependencies,
rank the earlier facts and report the recall of the true dependencies among the
first 8, 16, 32 and 64.  The port's matched harness runs the frozen Python v4
code and the port on the same corpus; both report the same recall summary to
the last printed digit.  The preview binary does not run this stage: the
port's search preparation, \code{(ai-math:search \$decls)}, returns no answer on
it, although loading the corpus works.  The table therefore measures the NIK

\subsection{What was not measured}
\label{app:runtimes-unmeasured}

\begin{itemize}
\item \textbf{The ai-mathematician beyond premise selection.}  Its proof stages
  call Vampire and Lean.  The port's Lean worker requires Linux user
  namespaces for its isolation, which the measuring session did not have, and a
  full discovery cohort takes about a day on two workers; the preview binary
  also fails the port's search stage (above).
\item \textbf{Other inductive-learning programs.}  The Popper, Hopper and IGGP
  programs in the tree replay the reference systems' published programs over
  every example rather than learn them, and the Metagol-style learners have no
  matching reference task here; Hopper's own learner is not runnable on this
  machine.  nuPLN's distractor ladder was not timed: with one always-true
  distractor predicate, \CeTTa{}'s depth-first search needed about seven
  minutes in an untimed run under load, and the faster first-witness strategy
  reported in September was never committed.
\item \textbf{Upstream Hyperon Experimental.}  Only the fork build named above
  was measured.
\item \textbf{Three rungs of the scale ladder}: Hexlife with 200 cells and 30
  generations, the counter machine at register value 1,000 and the process
  calculus at 500~$+$~500, each of whose MORK runs takes minutes at this load;
  and SWI-\PeTTa{} and MORK's default build at the ladder's sizes.
\item \textbf{The largest graph rungs} of Section~\ref{app:runtimes-earlier}
  on the preview.
\item \textbf{Portable wheels, physical AArch64 and recovery from allocation
  failure inside GMP} are not requalified by this appendix.
\end{itemize}
